# v5b：必填事件字段 + 消除统一拒绝的线索冲突

运行时间 2026-11-15 11:30–12:03（Asia/Shanghai），harness `e56a9e8`，入口 `benchmark/phase5b/ctl.py`。这是 phase5 的轻量包装：Oracle、数据库辅助和 145 项计分全部复用 phase5，只替换四个源码模板，并冻结进计划。仍是四个模型 × 10 块 × 2 组，并行运行，隔离方式同 v5。

## 与 v5 的两处差别

1. **action 组：Event 改为必填。** 内核新增 `action.NoEvent`，`Event` 为空时每次 Run 都报错，表现为 503，于是“漏填”从不会报错的静默缺陷变成会被显式契约测出来的失败。approve 示例同步改为显式写 `Event: action.NoEvent`。
2. **manual 组：消除统一拒绝的线索冲突。** v5 中 opus manual 组 0/10，原因是线索互相矛盾：原有的单条审批接口对缺失返回 404、对状态不符返回 409，与批量 Action 统一返回 409 的约定不一致，而 opus 照搬了前者。v5b 在 `approval.go` 和 `reject.go` 的统一 409 处加了一段注释，说明 Action 不同于 legacy 单条接口，不泄露采购单是否存在。这条约定因此改为“有注释”。

两组其余文件逐字节相同（`test_phase5b.py`）。控制结果：两份参考均 145/145，7 个隐含负控制只触发各自目标约定，5 个显式负控制被识别，另有崩溃控制和交接控制。**action 组的 omit-event 控制已从“隐含违反”变为“显式失败”**（116/133），与设计预期一致。

## 发生了什么

- **必填字段消除了“漏填”。** 在 action 组的 reopen 声明里，haiku 有 8 份写对 `purchase.reopened`、1 份写成 `purchase.resubmitted`、1 份写成 NoEvent；luna 9 份写对、1 份 NoEvent；qwen 有 8 份**主动选了 NoEvent**（4 份写 `action.NoEvent`，4 份直接写字面量 `"none"`），只有 1 份写对。也就是说，“必须明确表态”让多数模型从现有线索推断出要发事件，但 qwen 把“允许不发事件”理解成了默认答案。必填字段只能消除无意的遗漏，挡不住明确做出的错误选择。
- **线索冲突一旦消除，opus 的 manual 组就几乎全对。** 统一拒绝从 0/10 升到 10/10，manual 组 145 全过 9/10，唯一的失败是一次 reopen 重放返回了 409。这说明 v5 中 opus 0/10 的主要原因是 harness 的线索相互矛盾，不是推断能力不足；v5 的那列数据应理解为“遇到线索冲突时，模型会跟随最近似的既有接口”。
- **manual 组的自然违反依然存在。** requestHash 是 luna 6/10、haiku 7/10，典型错误是把 reason 也放进指纹；outbox 和统一拒绝在弱模型上也各有遗漏。

## 解读

- **把可省略的约定改为平台强制（fail-loud 加显式表态），能大幅减少漏实现。** haiku 和 luna 的 action 组从 2/10、0/10 升到 8/10、9/10。剩下的错误变成了“明确选错”，下一层防护需要语义校验，比如 Verifier 检查新操作的事件类型是否在 notify 消费者的列表里。
- **约定是否成立，取决于线索是否一致。** 存在冲突时，即使是强模型也会稳定地跟随另一种先例。这既是 harness 设计必须避免的问题，也对应真实代码库里新旧风格并存的情况。
- **v5b 修改了提示材料，不是对 v5 的重复实验。** 两处修改各自只影响一组，但两组在同一个队列里，比较 v4/v5/v5b 时应按约定逐列看。
