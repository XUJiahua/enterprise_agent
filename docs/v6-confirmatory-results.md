## 执行概况

- **规模**：3 个任务（T1 reopen 复现、T2 二级审批、T3 批量改派）× 4 个模型 × 10 块 × 2 组，共 240 个 trial。
- **结局**（240 个计划 trial）：
  - 220 个生成完成，其中 3 个在验收时启动超时或崩溃，记为 candidate-error，**实际完成评分的是 217 个**（86 个全部通过，131 个未通过验收）；
  - 8 个越界，7 个超出预算；
  - 5 个未测量：生成途中触发用量上限，按附录 E 不重跑。
  - 两组都已观察到的块有 115 个，用于 H2、H3、A。H1（K）要求两组都已评分，有效块为 **98** 个。
- **中断与续跑**：第一轮跑到中途触发 Kiro 月度用量上限（附录 E）。续跑时服务区域改到了 us-east-1（附录 F），隔离白名单随之更新，网络隔离控制重跑后 21/21 通过。被中断的 126 个 trial 当时都还没有开始生成，续跑时就是它们的首次生成；对应的预检记录已归档。
- **隔离**：全部 trial 都在网络受限的沙箱里生成。审计结果如下：
  - `retrieval-attempt`（嵌套 kiro-cli、curl、git clone、外部 URL）：0 个。因此敏感性分析与主分析完全相同。
  - `network-denied`：22 个，被拒的主机包括 cognito-identity / oidc（Kiro 刷新认证时访问）和 1 次 `proxy.golang.org`，都不是检索类主机。

## 次要与描述性结果

**全部用例通过率（A）不相上下：** 配对后只有 action 通过的块为 21，只有 manual 通过的块也是 21（p=0.56）。合计 manual 42/120，action 44/120。拉平的原因是 declared 约定，见下文。

| 指标（各层合计） | manual | action |
|---|---|---|
| K：内核封装约定全遵守（已评分的 trial） | 66/103 | 110/114 |
| E：显式契约全部通过 | 86/120 | 110/120 |
| D：作者需要声明的约定（outbox）得到遵守 | 57/103 | **44/114（0.39）** |
| A：全部通过 | 42/120 | 44/120 |
| 越界 | 4 | 4 |

- **D 未达预期。** 预注册写的是 action 组合并 D ≥ 0.6，实际是 0.39，没有达到。

  按任务看 action 组声明的 Event 值（`declared-event-values.json`）：

  | 任务 | 写对事件的 trial 数（opus / haiku / luna / qwen） |
  |---|---|
  | T1 reopen | 10 / 6 / 10 / 2 |
  | T2 countersign | 6 / 1 / 3 / 0 |
  | T3 reassign | 1 / 3 / 1 / 1 |

  T2、T3 中，**连 opus 也多数写了 `action.NoEvent`**。声明中显式写出 `NoEvent` 时，内核能挡住“漏填”，但挡不住“写成不发事件”。T2 的 notify.go 已注明“首次审批不发事件属历史例外，之后新增的 Action 都要发事件”，模型仍然照抄了与新操作最接近的那条既有声明：countersign 照抄了 approve；reassign 是新的 Update 类型，也照抄了 approve 的 `NoEvent`。这是本次最重要的新发现：**必须显式表态的声明字段，在任务语义与某个不发事件的既有操作相似时，会被系统性地填错，强模型也不例外。**
- **安全（U）：** 详见下面的“安全指标的修正”一节。按预注册检测器，U=0；放宽检测范围后，同样没有发现授权、资格或整批原子性类的越权写入。但存档的证据形状无法排除并发情形下的双重写入。

## 安全指标的修正（审阅后追加，探索性）

审阅指出，预注册的 U 检测器只做了两步匹配：先在错误字符串里找 `'state_changed': True`，再用正则 `authori|atomic` 匹配组名。这样会漏掉 `refused request mutated state` 这类错误形状，也会漏掉 eligibility、amount 等组。`research/v6_safety_rescan.py` 改为覆盖所有拒绝类组（authorization、eligibility、amount、assignee）以及各回归套件的前缀，同时识别三种证据形状：`state_changed`、`mutated state` 文本、以及预期拒绝却返回 2xx。它把失败分成以下几类；9 个人造的证据形状控制（包括审阅者描述的那种）都能被正确分类。

| 分类 | 失败用例 | trial 数 | 说明 |
|---|---:|---:|---|
| 未授权写入（拒绝类用例改变了状态，或返回 2xx） | 0 | 0 | 未观察到 |
| 批量部分提交 | 0 | 0 | 未观察到 |
| 副作用原子性破坏（注入 outbox 故障后业务状态仍提交） | 110 | 110 | 候选没写事件，注入的故障不会触发。这是 outbox 约定被违反的表现 |
| 幂等违规（同一个 key 换了参数仍返回重放的 200，存档未记录写入） | 8 | 8 | 全部在 manual 组 |
| 并发无法判定（两个并发请求都返回 200，存档缺少状态快照） | 10 | 10 | 全部在 manual 组；**可能是双重写入，现有证据无法确认** |
| 服务异常（预期 4xx 或 2xx，实际返回 5xx） | 162 | 12 | 没有写入证据 |

据此，正确的表述是：**没有观察到授权或整批原子性层面的越权写入；有 110 个候选在 outbox 故障下没有保持副作用的原子性；另有 10 个 manual 候选在并发下可能双重写入，但无法判定。** 这并不证明系统不存在越权漏洞。下一版 Oracle 应把这些分类记录为结构化字段，不再从错误字符串里反推。

## Verifier 样本外评估（附录 D：规则冻结在 `4e286c9`，原样运行）

共评估 228 个候选（含越界重建）。其中 110 个“显式全过、隐含违反”，规则拦住了 76 个。按候选统计：TP 104 / FP 11 / FN 38。

| 规则 | TP | FP | FN | 说明 |
|---|---|---|---|---|
| extension-scope | 8 | 0 | 0 | 8 个越界候选全部拦住 |
| event-consumer | 39 | 0 | 77 | **T3 action 组 32 个违反只拦住 1 个**：T3 的新声明类型 `action.Update` 不在冻结规则的 Kinds（Operation/Transition）里 |
| manual-event-consumer | 42 | 0 | 74 | |
| manual-fingerprint | 14 | **30** | 5 | **T3 manual 组 11 个通过验收的候选被误报**：v6b 的指纹按约定包含 assignee，而规则把它当作“非目标的输入” |

按候选比例计：补拦率为“显式全部通过、但隐含约定被违反”的候选中的 76/110≈69%；误拦率为完整通过的候选中的 11/86≈12.8%，这个比例作为强制 CI 门禁偏高。与样本内的 0 误报对比可以看出，规则在已见过的形态上可靠，但**无法自动泛化到新的声明类型或新的指纹约定**。Verifier 需要随内核一起演进，并为每个新扩展点补充控制用例。

## 分析偏离与审阅修正（读取结果后发生）

`analyze_v6.py` 第一版把**所有组**的 `state_changed=true` 都算作 U，比预注册的定义（只统计授权类、原子性类用例）宽。读取结果后发现了这个实现与文本不一致，已改为按文本定义计算。改动前后 H1–H3 没有变化。两版脚本都在 Git 历史中。审阅后又追加了两处修正，都不改变检验结果：（1）按假设分别报告有效块数，H1 为 98、H2/H3 为 115，32 对 1 及其 p 值本身无误；（2）新增上面的安全重扫，作为探索性分析。

## 解读与局限

- **能下的结论：** 在三个我们设计的任务、四个模型上，受保护内核封装的约定与显式契约，都在预注册的检验下复现了正确性收益；生成也更快。没有观察到越权写入。
- **主要保留：**
  1. K 在 action 组中**按构造**就几乎必然成立，H1 实际检验的是 manual 组会不会自然违反这些约定。
  2. T2 qwen 有 4 份 action 候选违反了统一拒绝约定：声明里漏了职责分离的配置，导致首审人与其他拒绝情形的状态码不同。所以“kernel”类约定也有一部分依赖声明是否正确。
  3. 约定和任务都由我们自己挑选。
  4. Oracle 和参考答案在公开仓库里；服务端检索未被证实排除（附录 A），审计中也没有发现检索尝试。
  5. 跨日续跑，服务区域发生了变化。
- **对平台设计的含义（在 v5/v5b 基础上更新）：**
  - 把不变量放进内核，收益稳定。
  - 要求显式表态只能消除“漏填”，消除不了“按相似先例填错”。需要的是**按语义推导默认值**（例如所有状态迁移默认发事件，豁免名单写在内核里），或者由 Verifier 校验“事件有消费者却声明不发”。后者要求规则覆盖所有声明类型，并且随内核一起更新。
