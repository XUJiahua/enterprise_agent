## 问题与执行

v7 和 v8b 中，目录条目都由平台方预先写好，A 达到 97–99%。v8a 要测的是：条目由 Agent 根据业务需求起草时，收益能保住多少；起草后再加一次 AI 审查，能挽回多少。

| 组 | 流程 |
|---|---|
| manual | 手写实现（与 v7 相同） |
| given | 平台给定正确条目，内核执行，Agent 只写适配 |
| drafted | 同一模型先起草 `catalog.go` 条目，必须通过 `Validate()`，否则记 draft-invalid，不重试；再开一个独立会话写适配 |
| drafted-review | 起草和适配之间插入一次审查，审查者固定为 claude-opus-5.5，只能修改 `catalog.go` |

- **任务**：2 个未公开任务。`return.v8` 是单目标状态迁移：第二位审批人把待会签的采购单退回给申请人。`bulk-delivery-site.v8` 是带参数的批量字段修改：申请人批量修改收货地点。
- **模型与规模**：3 个模型（opus、luna、qwen）。第一阶段 8 块 × 4 组，共 192 个 trial。按预先写好的规则进入第二阶段后，给 given 和 drafted-review 两组各补 8 块，共 96 个 trial。合计 288 个 trial，全部有观察值，没有未测量。
- **消耗**：第一阶段 392.2 credit，第二阶段 228.9 credit，合计 621.1，低于附录 B 的上限 650。
- **审计**：发现 2 个 `retrieval-attempt` 标记，都是 qwen 用 curl 探测本地 `127.0.0.1:8080/health`，不是外部检索，属于审计正则的误报。敏感性分析排除这两个 trial 后，结论不变。

## 主假设 H1：drafted-review 不劣于 given（界值 10 个百分点，Tango 检验，O'Brien-Fleming 两阶段）

| 阶段 | 有效块 | 只有 drafted-review 通过 | 只有 given 通过 | 差值 | z | 临界值 | 置信区间 | 决策 |
|---|---:|---:|---:|---|---|---|---|---|
| 第一阶段 | 48 | 1 | 4 | −6.3 pp | 0.75 | 2.96 | [−25.9, +12.2] pp（1−α₁） | continue |
| 第二阶段（合并） | 96 | 2 | 9 | **−7.3 pp** | 0.75 | 1.97 | **[−15.2, −0.6] pp**（1−α₂） | **不成立（not-noninferior）** |

**结论**：H1 不成立，无法证明“起草加审查”在 10 个百分点内不劣于平台给定的条目。置信区间的上界低于 0，说明 drafted-review **确实比 given 差**，点估计为 7 个百分点，95% 区间约在 1 到 15 个百分点之间。

## 条目正确性 C（第一阶段）

| 组 | C 正确 | 错误字段分布 | C 与 A 的关系 |
|---|---:|---|---|
| drafted | 36/48 | **event 11 次**，name 1 次，其余 17 个字段都是 0 | C=1 时 36/36 通过；C=0 时 0/12 通过 |
| drafted-review | 44/48（审查前 41/48） | **event 4 次**，其余都是 0 | C=1 时 44/44 通过；C=0 时 0/4 通过 |

- **审查的效果**：审查修正了 3 个错误草稿，没有改坏任何正确草稿；有 4 个错误草稿审查后仍然是错的。
- **错误全部集中在一个字段**：起草的条目里，事件、指纹、记录表、职责分离、拒绝语义等 17 个字段全部写对，**只有 event 会出错**（选择不发事件，或者事件名不对）。这和 v6 的 D 一致：Agent 不容易判断“这个新操作要不要发事件，发什么事件”。
- **条目写对就能通过**：在本设计里，条目只要正确，下游适配就一定通过验收（80/80）。所以收益损失完全来自条目错误。
- **按通道看**：错误集中在 qwen 和 luna 的 delivery-site 任务。drafted 组 qwen 0/8、luna 6/8；drafted-review 组 qwen 4/8、luna 8/8。opus 在所有通道全对。

| 类别 | manual | given | drafted | drafted-review |
|---|---:|---:|---:|---:|
| double_apply（并发重复生效） | **6 个 trial** | 0 | 0 | 0 |
| service_error | 1 | 0 | 0 | 0 |
| 其余五类 | 0 | 0 | 0 | 0 |

起草组即使条目写错，也没有出现越权或重复生效。条目错误只会导致事件缺失之类的功能性失败，事务、锁和职责分离仍然由内核保证。

## 成本：每得到一个正确结果（第一阶段，块级 bootstrap 95% 区间）

| 组 | credit / 正确 | 时间 / 正确 |
|---|---|---|
| manual | 2.60 [2.10, 3.34] | 223 s [163, 317] |
| drafted | 2.36 [1.96, 2.85] | 204 s [150, 282] |
| drafted-review | 4.39 [4.06, 4.74] | 253 s [221, 291] |
| given | **0.83 [0.73, 0.93]** | **79 s [66, 95]** |

审查用的是 opus，每次大约 2.3 credit，所以 drafted-review 每个正确结果的花费比手写还高。平台方预先写好条目（given）的成本最低，但这里**没有计入**平台方写条目本身的人力成本。

## 解读

- **对 POC 的回答**：
  - 由 Agent 起草目录条目，仍然比手写好（H2）；
  - 加一次 AI 审查能挽回大部分损失（H3），A 从 75% 提高到 92%；
  - 但仍然**达不到**平台给定条目的水平（H1 不成立，约差 7 个百分点），而且审查让成本超过了手写。
- **错误集中在 event 一个字段，所以有针对性的办法**，可以在 v9 检验：
  1. 平台把“状态迁移和受管列修改默认发事件”写成内核规则，豁免需要单独审批；
  2. Verifier 检查新条目的事件是否在 notify 消费者中出现；
  3. 让审查只针对 event 字段，降低成本。
- **局限**：
  1. 只有 2 个任务，而且都是简单形状；
  2. 审查者固定为 opus，在 opus 通道上相当于自审；
  3. 正确条目的“唯一性”是论证出来的，不是证明出来的；
  4. 模型间差异很大，opus 在各组都全对，结论主要由弱模型驱动；
  5. Verifier 不检查条目本身是否正确，所以它的结论没有计入 C 或 A。
