## 已有证据支持什么

1. 在这里的闭合采购模型和固定五类故障下，Handler 漏写条件不一定会造成漏洞；正确配置的 ORM 或数据库约束可在下一层阻断。
2. 最小 Go 方案已能处理这些基础不变量，暂时不需要建设完整 ORM 或业务 DSL。
3. 验收不能只检查正确路径。普通 Go 的注入版本暴露缺陷，验证了 Oracle 对这些错误的敏感性。
4. 策略层也会被误用。ZenStack 改用未安装 PolicyPlugin 的原始 Client 后，跨租户读取再次发生；这是预期边界反证。
5. 权限语义存在产品代价差异：Go 的列权限拒绝敏感列过读时整个请求返回 403；ZenStack 仍返回记录，但将字段置 null。

## 目前不能得出的结论

- 不能从五类固定注入推出真实 AI 缺陷率降低多少。
- 不能证明任意 Go 扩展无法绕过安全边界；同进程代码仍可获得数据库凭据并伪造会话上下文。
- 不能据此判定 ZenStack 与 Go 哪个开发成本更低、性能更好或真实首次通过率更高。
- 不能把有限 SQL 子集校验等同于任意迁移的安全证明。

下一轮优先冻结独立验收，再测试“新增敏感字段 / 新增列表 API / 新增后台动作 / 改动审批规则 / 新增业务表”等真实 AI Coding 任务。规则写错与策略未启用必须纳入试验，不能只测试规则已经正确时的业务漏写。
