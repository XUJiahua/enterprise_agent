# PR #7 后续研究：护栏能保护什么，还缺什么？

2026-11-14。来源：PR #7 的 `5ab6856c7750722910471b5a5bd19a4ac1b1b079`，只对 `pilot-handoff-003` 的九个既有候选作统计。首批三个准备条件不同的样本保持单独报告。

**九项首次通过验证了真实执行链路。进一步的重放表明，行级护栏可在新接口漏写租户条件时继续保护数据；批量业务的“全批成功”则需要额外的 Action 契约。** 这是机制与边界研究，还没有测出真实模型缺陷率的变化。

## 本轮实际做了什么

- 校验归档 SHA256 清单的全部 139 个文件，并核对完整覆盖。
- 从冻结 harness 的 Git 对象重算计划中的源码 checksum。
- 逐项核对 plan、batch、独立验收、原始事件 usage 和 bundle HEAD 的候选身份。
- 从九个归档 bundle 恢复候选，在原始冻结 harness 上重新执行 195 项验收，全部通过。
- 对恢复后的候选追加 45 项事后数据变换测试，全部通过。
- 只移除三个真实生成汇总接口的显式租户过滤，观察原有策略层能否继续保护结果。
- 在实际 RLS 数据库上比较“只依赖行策略”和“检查受影响目标数并回滚”的批量行为。

**本轮新增模型生成数为 0。** 重放不是新样本，人工修改不是模型输出，追加测试不回写 PR #7 的首次通过率。

证据：[审计 JSON](evidence/research-followup-2026-11-14/pilot-audit.json)、[重放与干预 JSON](evidence/research-followup-2026-11-14/followup.json)。本地研究使用真实 PostgreSQL 18.6；CI 使用 PostgreSQL 17.6，分别记录结果。

## 1. 原始数据足以支持哪些判断

| 路径 | 任务数 | 原始首次通过 | 生成耗时均值/秒 | 非缓存输入 token 总和 | 输出 token 总和 |
|---|---:|---:|---:|---:|---:|
| 普通 Go | 3 | 3/3 | 36.807 | 46,915 | 2,891 |

| ZenStack V3 | 3 | 3/3 | 55.314 | 48,339 | 4,811 |

非缓存输入为实际上报的 input_tokens 减 cached_input_tokens；缓存是输入的子集。表中生成时间不包含依赖准备或独立验收。服务端不可变模型快照及实付费用未知。

这些只是各三个不同任务的描述统计。模型环境、缓存、语言工具与代码路径都有影响，不能据此认定某框架普遍更快、更便宜，或推导总体成功率。九个任务全过，当前通过率指标没有产生可比较的差异；直接重复更多同类简单读任务，未必能有效回答护栏收益问题。

## 2. 对真实生成代码移除租户条件，结果如何

原来的三个新汇总接口都显式限制当前租户。这里人工移除新接口的那一条过滤，保持身份、客户端配置和底层策略不变。修改范围有精确断言与独立 patch；未改动历史证据。

对 Alice 的预期汇总为 count=4、totalAmount=800：

| 真实候选的技术路径 | 原始接口 | 人工去掉接口租户过滤后 | 隔离与可用性 |
|---|---|---|---|
| 普通 Go | 4 / 800 | **5 / 1200，含 tenant-b** | 发生泄露，HTTP 200 |
| Go + Policy/RLS | 4 / 800 | 4 / 800 | 隔离保留，HTTP 200 |
| ZenStack V3 | 4 / 800 | 4 / 800 | 隔离保留，HTTP 200 |

Dave 和 Carol 视角也按各自租户验证，共九个请求。这里无需把报错或不可用视为成功拦截。

得到的结论是：**对已正确配置的策略，接口层遗漏过滤的后果可被下一层约束消除。** 但这个遗漏是人工制造的，不能报告成“模型生成了三个权限错误”或模型自然错误率。

另外，在 guarded 应用里，省略显式租户条件也可能是有意委托给平台；判断正确性应以端到端权限行为为准，不能把源码里没有 WHERE tenant 直接当成缺陷。

## 3. 重要边界：行权限与批量业务契约

在真实 RLS 环境中，Carol 以 tenant-a 审批人身份请求同时批准：

- `a-other`：有权访问和审批；
- `b-other`：属于 tenant-b，无权审批。

测试直接使用运行时非特权账号，在事务内执行一次针对两个 ID 的 UPDATE，并记录最终数据库状态：

| 处理方式 | UPDATE 影响行数 | a-other | b-other | “整批失败则全部不变”契约 |
|---|---:|---|---|---|
| 仅由 RLS 过滤，再提交事务 | 1 | approved | submitted | **不满足** |
| 同一事务检查应完成两个目标；不足则回滚 | 1，随后 rollback | submitted | submitted | 满足 |

第一种情况，数据库完整地提交了匹配的一行，租户隔离仍然正确。API 的业务语义要求两个目标全批成功，就必须额外检查完整目标集合，并在不足时回滚。只检查 HTTP 错误或无权行未变，容易漏掉有权行已经部分提交的缺陷。

这是手工构造的业务契约探针，不是现有模型生成接口的已发现漏洞。PR #7 尚未实现批量审批。

### 对应用内核的具体建议

除了行/字段授权，应优先提供受控 Action 的事务与结果约束：

1. 输入目标集合明确，空、重复、超量与非法类型在执行前处理。
2. 授权与状态条件进入实际更新操作；避免只在事务外读取检查。
3. 若业务要求全批成功，在同一事务内校验实际完成的目标集合。
4. 校验失败时回滚，不把“返回一个 HTTP 错误对象”误当成事务失败。
5. 通过后置数据库状态和并发场景验收完整业务不变量。

这可以先做成小型 Go Action 接口与确定性验证规则，不要求马上发明完整业务 DSL。哪些业务允许部分成功，应由显式契约决定。

## 4. 还有一个值得纳入验收的差异：查询形状

PR #7 的两个 ZenStack 候选选择了：

- 汇总：findMany 读取本租户全部 amount，再在 JavaScript 中 reduce。
- 标题搜索：findMany 读取本租户全部记录，再在 JavaScript 中 filter/includes。

当租户有 N 条记录时，当前候选会在应用侧物化这些记录。相应 Go 候选把 SUM/count 或 strpos/lower 条件放进 SQL。小数据功能验收全部通过，但资源使用和扩展性尚未测量。

这反映的是这两个模型候选选择的实现方式，不是 ZenStack 无法执行数据库聚合或过滤。下一轮应显式加入查询下推、结果/内存上限和性能预算，再单独测量；不能把生成耗时当成运行时性能。

## 5. 下一轮应怎么测

先新增一个真正有区分力的任务：**原子的批量审批**。输入混有本租户/其他租户、自己/他人、已审批/未审批以及不存在的目标，要求整批成功或整批不变，再加入重叠并发批次。

Go 采用 2×2 设计，才能分别估计流程与 Runtime 约束的作用：

| Cell | Go Runtime | 额外开发流程指导 |
|---|---|---|
| go-ordinary | 原有手写授权 | 无 |
| go-process | 同一原有 Runtime | 不变量清单、先列失败场景、运行可见测试、检查 diff |
| go-runtime | Policy/RLS | 无 |
| go-runtime-process | Policy/RLS | 同一流程指导 |

ZenStack 作为补充框架参考，单独报告；Go 四个 cell 才构成相同代码基础上的流程 × Runtime 比较。所有 cell 都必须获得相同完整业务要求，不能通过少给 baseline 需求制造差异。

评分至少拆成：授权操作能完成、逐行/租户安全、全批语义、并发、原有回归。预先拒绝所有请求可以保护数据，但不能算功能通过。

[机器可读预注册草案](../research/phase2-preregistration.json) 定义了首个任务、五个 cell、分组评分及人工正反控制。它是设计草案，**不是可直接交给现有 benchctl v1 的可执行计划**；driver 的 cell/流程提示词哈希、独立隐藏 Oracle 和分批汇总仍需实现，关联 #5、#6。

先用小型平衡 pilot 判断任务是否有区分力，再按声明的效应量与 pilot 方差规划确认性样本。十次重复本身不自动带来统计显著性。确认性队列启动前，应冻结采样规则、模型请求、CLI/全局配置、预算、任务与隐藏样本。

## 复现本轮研究

在包含 PR #7 历史的独立分支准备 Go、Node、ZenStack 依赖和可销毁 PostgreSQL，使用 README 的数据库变量：

```bash
python3 research/audit_pilot.py

```

如已有同名研究输出，使用 `--out reports/research-another-run`。端口沿用 POC_HTTP_PORT，默认 8080。研究 runner 会从归档 bundle 恢复候选，临时 worktree 在结束时清理；原始证据不会覆盖。

Public CI 在 baseline job 中运行本研究的全部路径，然后打包原始重放日志、精确人工修改 patch 及研究 JSON。这里的 baseline 是运行该研究任务的 CI job 名称，研究本身覆盖三条技术路径。
