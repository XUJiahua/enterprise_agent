## 四个真实实现有什么差别

| Cell | 100 个目标的锁定 SELECT 数 | UPDATE 数 | Handler 请求体显式上限 | 71,719 字节合法 JSON 探针 |
|---|---:|---:|---|---|
| go-ordinary | 1，集合查询 | 1 | 无 | 200，完成整批 |
| go-process | 100，按排序逐个查询 | 1 | 65,536 字节 | 400，数据不变 |
| go-runtime | 1，集合查询 | 1 | 无 | 200，完成整批 |
| go-runtime-process | 1，集合查询 | 1 | 65,536 字节 | 400，数据不变 |

SELECT/UPDATE 数来自这四份源码的正常成功路径分析，没有伪装成 SQL tracing 或延迟测量。表中不含事务、身份绑定和启动检查。`go-process` 在循环中逐个 `QueryRow(... FOR UPDATE)`，其余三组以 `ANY(ids)` 集合查询锁定目标。这是一个候选的额外数据库往返，不能解读为流程指导必然产生 N+1，更不能当作框架性能结论。

容量探针使用相同的小型有效请求，仅增加 70 KiB 合法 JSON 前置空白。两份实现用了 64 KiB MaxBytesReader，两份使用无显式上限的 ReadAll。拒绝超量请求本身可以是合理策略；问题是当前契约没有明确最大报文与对应状态码。这是需要统一的 API/资源边界，单独登记，不向原始首次评分追加新规则。下一版契约应预先明确最大报文、超限响应，以及与合法输入边界相匹配的正例。

## “额外指导”不等于“有测试/无测试”

四个候选都自行创建了一个 Go 测试文件，原始事件中每个候选都有两条成功完成、包含 `go test ./...` 的命令。无额外指导的两组同样自发编写测试，因此四组实际执行策略存在重叠。

本实验的处理变量是是否增加那段流程提示词。不能把 ordinary 组解释成完全不测试，也不能把全部通过解释成测试流程无效。四个单样本全部通过，仍然不足以估计总体正确性或比较平均成本/性能。

## 实际观察到的隔离边界

两个带额外流程指导的候选在枚举 AGENTS.md 时，显式搜索过候选目录外的宿主路径。这是原始命令事件中可核对的目录枚举行为；当前审计并不证明它们读到了 Oracle、私有 seed 或参考答案，也不将其判作已发生答案污染。

这说明最小源码导出与“不要读其他目录”的提示，仍不能构成严格盲测。下一轮确认性实验应让生成端只能挂载候选与公共测试材料，移除宿主其他 checkout、共享私有数据库和可读答案；生成与独立验收分开运行。记录 CLI 配置 fingerprint 也不等于完整封装全局技能配置和服务端模型快照。

## 下一轮研究方向

目前不应仅靠重复相同的单次新增接口任务来强行制造差异。更值得验证的是平台能否在后续修改中持续维护不变量，以及能否减少应用层反复实现的工作：

1. **统一可执行 Action 契约**：输入集合、权限条件、事务内完整目标检查、后置条件、拒绝回滚。行级 RLS 继续负责行/字段权限，Action 负责业务集合语义。
2. **统一工程约束**：明确报文上限/状态码、数据库调用预算、公共测试服务条件，并在新队列启动前冻结；不要只追求增加反例数量。
3. **真实业务演进任务**：例如批量审批新增必须同事务提交的审批日志与幂等语义，用触发失败、重复请求和并发校验审批状态及日志集合。它需要新的任务/验收版本，不能回写本轮计划。
4. **分开估计两个问题**：未经人为干预的生成结果衡量真实实现能力；人工漏掉约束或后续变更衡量平台对明确故障的容错。二者单独报告。

上述是下一轮设计建议，尚未实现新的 Action 内核、审批日志或幂等功能，也没有启动新的真实模型队列。

## 复现

在包含原归档的 checkout 中，依 README 准备 Go、Node/pg、Python 和可销毁 `_poc` PostgreSQL，设置数据库环境变量与 `POC_DB_RESET=1`：

```bash
python3 research/audit_atomic_pilot.py
python3 research/replay_atomic_pilot.py
```

输出位于 `reports/atomic-followup/`。已有输出不覆盖，第二次使用 `--out` 指定新的文件/目录。端口由 POC_HTTP_PORT 控制。程序不读取原私有 seed，不调用模型，不修改候选，编译二进制只保留在临时目录并在结束后移除；CI artifact 保存 JSON 与测试/应用日志。
