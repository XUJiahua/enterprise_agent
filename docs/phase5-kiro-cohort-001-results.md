## 发生了什么

**1. 显式契约：action 组略好。** action 组显式全过 39/40，manual 组 33/40。manual 组的显式失败都落在 reopen 的并发与幂等上，这正是 v3 里弱模型手写时最容易出错的地方。

**2. 由内核封装的三条约定（audit、hash、统一拒绝）：action 组 117/117 全部遵守。** manual 组出现了以下自然违反：

- **opus 统一拒绝 0/10**：10 份全部对"不存在"返回 404、对"存在但状态不对"返回 409，这会泄露采购单是否存在。需要注意，这条约定没有注释，线索互相冲突：批量 Action 统一返回 409，而原有单条 API 的 `ErrNoRows→404` 又指向 404。opus 的选择本身"有据可依"，所以这一列反映的是"无注释且线索冲突的约定几乎不会被推断出来"，不应解读为 opus 能力不足。
- **luna requestHash 5/10**：典型的错误是把 reason 也放进了指纹，写成 `Fingerprint(opReopen, []string{id, reason})`。
- **haiku 和 qwen**：四条约定都有零散违反。

**3. 内核没有封装的那条约定（outbox）：action 组反而更差。** action 组需要在声明新操作时自己填 `Event: "purchase.reopened"`。结果只有 opus 10/10 填对；haiku 2/10，luna 0/10，qwen 0/9。没填对的候选里，多数没有写 Event 字段，少数写了 `Event: ""`。

同样这条约定，manual 组是 10、5、10、6。原因是 manual 组有现成的 `reject.go`，里面有完整的事件 INSERT 可以模仿；action 组能参照的 `Approve` 声明本身就不带 Event，notify.go 里还写着 "Approvals predate the outbox"。Transition 的 Event 字段可以省略，省略时内核静默地不写事件，所以漏填既不会编译失败，也不会运行时报错。

## 解读

- **平台只对它封装了的部分有正确性收益。** 审计、指纹、统一拒绝由内核实现，action 组在四个模型上全部遵守；manual 组在每个模型上都有自然违反，其中两条一个是线索冲突（opus），一个是需要跨文件推断（luna）。
- **声明式扩展会带来新的失败形态：可省略字段的静默默认值。** 弱模型普遍漏填 Event，而内核把"没填"当成"不需要"处理。平台设计应该把这类字段设为必填、要求显式写"无"，或者用 Verifier 检查"新操作是否声明了事件"，不应依赖模型推断。
- **强模型（opus）**：action 组 10/10，manual 组 0/10；manual 组的失败全部来自那条无注释、线索冲突的统一拒绝约定。
- **弱模型**：两组的全过率都很低，失败原因不同。manual 组的失败分散在各条约定和显式的并发问题上，action 组集中在 outbox 一条上。
- **效率**：action 组在四个模型上都更快、更省，中位耗时少 27–41%。
- **结论边界**：四条约定由 harness 作者挑选，统一拒绝的线索存在歧义，统计为事后选定，只有一个任务。这些结论只适用于本设计。

## 局限

- 隔离只覆盖文件系统，网络不受限，不能称为盲测。PostgreSQL 版本为 17.11。四个队列并行运行，耗时可能受影响。
- 设计文档已经说明：统一拒绝有一部分由 RLS 兜底，用加锁读取的候选会自动满足这条约定。尽管如此，opus 的 manual 组仍然 10/10 区分了 404 和 409。
