# 实验总结（2026-11-15，2026-11-16 更新）：AI Coding 在企业平台能力上是否更稳定

> **2026-11-16 晚更新：v7 预注册确认性实验完成**（[v7 结果](v7-confirmatory-results.md)，240 个 trial，2 个未公开任务，Oracle 私有，生成与验收分属两台主机）。平台预先给定权威业务语义（受保护的操作目录 + 内核执行）后：
> - 完整验收成功率 A：手写 55% → 只读文档 76% → 内核执行 **99%**；
> - H1 35 对 1，p≈5×10⁻¹⁰；H2、H3 均成立，说明权威事实和内核执行两种来源都有贡献；
> - 每个正确结果的 credit 从 2.32 降到 0.81；
> - 手写组有 8 个 trial 并发双重生效，opdef 组为 0；
> - 冻结 Verifier 首次样本外评估：误拦 0/184，阻断 48/50。
>
> v6 中局部收益被声明层错误抵消的问题，在 v7 中通过“由平台决定哪些业务语义”得到解决。

> **2026-11-16 更新：预注册的确认性实验已完成**（[v6 结果](v6-confirmatory-results.md)，240 个 trial，3 任务 × 4 模型，网络受限生成）。三条主假设在 Holm 校正后都成立：
> - H1（内核封装约定）：98 个两组都已评分的块中 32 对 1，p≈8×10⁻⁹；
> - H2（显式契约）：115 块中 26 对 7，p≈7×10⁻⁴；
> - H3（耗时）：中位每块少 22 s。

> 没有观察到授权或整批原子性层面的越权写入；另有 110 个候选在 outbox 故障下没有保持副作用的原子性，10 个 manual 候选在并发下可能双重写入，现有证据无法判定（审阅后的安全重扫）。全部用例通过率两组持平（42 对 44/120），拉平原因是需要声明的事件字段：T2/T3 中模型（含 opus）普遍照抄最相似的既有声明，把事件写成 `NoEvent`。冻结 Verifier 在样本外出现两类泛化失败：新声明类型漏检，新指纹约定误报。下文是 v1–v5b 的探索性结论；凡与 v6 有出入之处，以 v6 为准。

本文汇总 v1–v5b 的真实模型实验，供合并前审阅。各阶段的细节和证据见文中链接。所有数字均为冻结计划下的**首次成绩**；事后诊断单独标注，不改写首次成绩。

## 一句话结论

平台能力（受保护的 Action 内核 + RLS 护栏）带来的正确性收益，**只体现在它真正封装的那部分规则上，并且只在模型较弱、或任务需要从零手写难点时才显现**。效率收益（耗时、credit）则在几乎所有条件下都存在。平台本身也会引入新的失败模式：

- 扩展点不明显时，模型会去改平台代码；
- 可省略的字段会被静默漏填。

这两类问题都要靠平台设计和 Verifier 来防，靠提示词不够。

## 主要发现

1. **护栏机制有效，并且失败时站在安全一侧。** 5 类人工注入缺陷中，普通 Go 实现一类都没拦住，RLS 和 ZenStack 拦住了全部 5 类（v1 阶段）。在之后所有真实失败的候选中，**没有观察到越权或跨租户写入**；失败表现都是“过度拒绝”，或者某条约定没遵守。
2. **规格清楚、难度适中的任务上，强模型不需要平台。** opus 在 v3、v4 两组都是 10/10，Codex 的 16 个候选也全部首次通过。
3. **从零手写事务和幂等时，平台对弱模型帮助明显。** v3 队列 003 中 manual 组为 5/10、3/10、1/10，action 组为 8/10、10/10、6/10；差距集中在幂等和并发。
4. **起点有可照抄的同形实现时，“约定只写在代码里”并不难。** v4 中 manual 组 40 个候选里只出现 1 次自然违反。
5. **没有可照抄范例、约定线索分散时，manual 组会自然违反约定，而内核封装的约定在 action 组 100% 被遵守。** v5/v5b 中 action 组在审计、指纹、统一拒绝三条约定上为 236/236；manual 组则反复出现“把 reason 计入 hash”“漏发事件”“拒绝时区分缺失和无权”等问题。
6. **平台引入的两类新失败，都能通过平台设计缓解。**
   - **扩展点不明显**：v4 中 haiku 和 qwen 的 action 组 20/20 都把新声明写进了受保护内核。v4b 加一句提示后，越界率降到 30–40%。事后诊断表明，这 20 份候选本身的行为都是正确的。
   - **可省略字段静默生效**：v5 中弱模型漏填 Event，action 组只有 2/29 正确。v5b 改为必填，并要求不发事件时显式写 NoEvent 后，haiku 和 luna 升到 8/10、9/10；qwen 则有 8/10 主动选择了 NoEvent，属于“明确选错”。
7. **harness 自身的缺陷会伪装成能力差异，必须提前排查。** 已发现的三例：
   - pilot 001：Oracle 检查了契约中没写的 hash 公式；
   - v3：构建产物被误判为越界，候选崩溃被误判为基础设施故障；
   - v5：统一拒绝的线索互相冲突，导致 opus 的 manual 组 0/10；v5b 消除冲突后为 10/10。
8. **效率收益稳定。** 除 v4 中越界的那两个模型外，action 组的生成耗时和 credit 都更低。在 opus 上约少一半，在弱模型上少 20–45%。

## 对平台设计的含义

- 能封装的不变量（事务、审计、幂等、指纹、拒绝语义）尽量放进受保护的内核。这是正确性收益的来源。
- 扩展点要放在候选可编辑的包里，附上示例，并用作用域检查兜底。不能只依赖提示词。
- 声明式配置中的关键字段要设为必填、要求显式表态（fail-loud），并由 Verifier 校验语义，例如事件类型是否有对应的消费者。
- 不同风格的旧代码与新约定并存时，应在代码里明确说明以哪个为准，否则强模型也会照搬旧接口的写法。

## 仍不能下的结论

- 无法给出总体缺陷率的下降幅度，也不能推出通用低代码平台的收益。每种设计只测了一个任务，约定由我们自己挑选，存在选择偏差。
- 统计检验都是事后选定、没有预注册的探索性分析，每个模型、每个条件只有 10 块。
- 隔离只覆盖文件系统（Seatbelt）。网络没有限制，生成和验收在同一台机器、同一用户下进行，公开仓库中含有 Oracle，因此**不是盲测**。
- 本地 PostgreSQL 为 17.11，CI 为 17.6；haiku 和 qwen 不支持 effort 参数；credit 是计量值，不是账单。

## 建议的下一步

1. 预注册一个确认性实验：固定 v5b 设计，换 2–3 个新的业务任务，预先写定假设与检验方法。
2. 隔离部署到 VM 或容器，并限制网络访问，满足盲测条件。
3. 把“新操作必须声明事件且有消费者”“扩展只能写在 candidate 包”做成 appctl Verifier 规则，并测量它们的拦截率。
4. 把 phase4、phase5、phase5b 的控制接入 public CI。
