# v0.1.1 Agent 扩展试验（2026-11-18）

问题：在 v0.1.1（main `12624b3`）上，Agent 只读 `AGENTS.md` 和一段需求，能否正确扩展采购应用？哪些错误被平台拦下，哪些漏过？

这是**小样本功能反馈**：3 个任务，每个任务 1 次，没有对照组，也不做统计检验。它的用途是决定还要把哪些约定收进平台，不用来估计缺陷率。

## 设置

- 3 个 Kiro agent，都是 `claude-sonnet-5.5`，`kiro_default` 模式。每个 agent 在各自的 Paseo worktree 中工作，基于 main `12624b3`，在本地分支提交，不 push。
- 提示词只有一段公共说明（阅读并遵守 AGENTS.md、数据库 URL、交付方式）加一段需求。下表是需求摘要，原文保存在本机。
- 隐藏验收测试由我在试验前写好，放在仓库外，agent 不可见。评估时把测试复制进 agent 的提交，用真实 PostgreSQL 17.6 运行。
- 评估分三层：
  1. 隐藏测试；
  2. AGENTS.md 规定的检查，以及 smoke；
  3. 独立 reviewer（Paseo agent，codex-proxy/gpt-6-astra）对照需求与 AGENTS.md 找隐藏测试漏掉的缺陷。每条结论都附有探针输出或代码证据：界面、文档和版本问题来自代码检查，其余来自运行探针。

| 任务 | 需求要点 | 提交 |
|---|---|---|
| reject | `procurement.reject@1`：审批人批量驳回 submitted 单，原因必填，不能驳回自己的单；rejected 为终态；发 `procurement.purchase.rejected@1`，并给创建人发通知 | `853ffde` |
| amend | `procurement.amend@1`：创建人修改自己 submitted 单的金额（1–1e12），批准后不可改，审计记录前后金额 | `6eeb627` |
| reverse | `procurement.reverse-receipt@1`：申请人对 approved 单冲正一部分验收金额，冲正额不超过净验收；关闭时按净额判断；验收记录保持只追加 | `aabf7a1` |

## 结果

| 任务 | 隐藏测试 | AGENTS.md 检查 | smoke | reviewer 结论 |
|---|---|---|---|---|
| reject | 通过 | 通过 | 失败（迁移版本号写死） | FAIL：界面把 rejected 显示为空状态，驳回通知也显示成"已关闭"；文档未更新 |
| amend | 通过 | 通过 | 失败（迁移版本号写死） | FAIL：数据库没有金额上限，直接 SQL 可写入 1e12+1；文档仍写"金额不可修改" |
| reverse | 通过 | 通过 | 通过 | FAIL：照搬了需求里没有的 1e12 上限，合法的大额冲正被拒；改变了 `close@2` 的判断语义和 `closed@1` 的载荷含义，但没有升版本 |

三个 agent 都在规定的修改范围内工作：没有改动 `kernel/`、已发布的 migration、历史目录，也没有改已发布版本的 `contract.json` 定义。

## 写对的部分：平台保证与 agent 遵守的约定要分开看

**内核或数据库确定性保证**（agent 写错也会被拦下）：
- 指纹、重放与冲突、统一拒绝消息、按 ID 比对完整目标集合、零部分提交、事件与消费者一一对应，以及 0007 已有的触发器不变量。三个操作都声明了 `Definition.Targets`，隐藏测试中的 replay、conflict 和零写入拒绝全部通过。

**agent 遵守了领域约定**（平台不强制，这次做对了）：
- **父单锁协议**：三个 agent 都先 `lockPurchases` 再检查。reviewer 做了以下并发探针，结果都正确：
  - amend 与 approve，两种先后顺序；
  - reject 与 approve；
  - 冲正与关闭，两种先后顺序，包括通过直接 SQL；
  - 并发冲正，以及多行冲正超额。
- **数据库不变量的扩展**：
  - reject 扩展了 0007 触发器：rejected 是终态，直接 SQL 也不能让它转出。
  - amend 规定只有创建人能在 submitted 状态下改金额，批准后金额冻结。
  - reverse 给冲正表加了插入触发器：先锁父单，再按净额检查。
  
  例外：amend 没有在数据库里加金额上限，直接 SQL 可以写入 1e12+1，见下一节。
- **新表**：reverse 的新表做了 `FORCE RLS`、`RESTRICTIVE` 租户策略和列级授权。reviewer 额外加了一条 permissive 策略，租户隔离仍然成立；跨租户访问也被拦下。
- **消费者**：reject 扩展了消费者并严格校验载荷，通知经由独立的消费者角色投影。

v0.1 分析中担心的锁协议、拒绝语义、指纹和职责分离，这次都没有出错。拒绝语义和指纹现在由内核保证；锁协议和职责分离仍靠 agent 遵守 AGENTS.md，这次三个 agent 都遵守了，但这不是平台保证。

## 漏过的部分，以及 v0.1.1 之后的处理

| 缺陷 | 出现在 | 原因 | 处理 |
|---|---|---|---|
| smoke 写死了迁移版本号 | reject、amend | 隐含约定；AGENTS.md 没要求运行 smoke | smoke 改为读取最新 migration 编号（本 PR）；AGENTS.md 要求改动 migration 时运行 smoke |
| 新状态和通知类型在界面上显示错误 | reject | AGENTS.md 没提界面 | AGENTS.md 第 7 步要求同步 `statusLabel`、通知文案和代理允许列表 |
| 文档与实现不一致 | reject、amend | 同上 | AGENTS.md 第 7 步要求同步 `docs/kernel.md` |
| 数据库缺少数值上限 | amend | API 层和数据库层规则不一致 | AGENTS.md：需要上限时同时加 `CHECK`；测试要覆盖边界 |
| 照搬需求里没有的上限 | reverse | 复制了相邻操作的写法 | AGENTS.md：数值上下限只按需求写 |
| 改了其他已发布操作或事件的语义却没升版本 | reverse | `appctl validate` 只比对定义元数据，看不到 Execute 的行为 | AGENTS.md 举例说明"顺带改动也要升版本"。**确定性检查仍然做不到**，这是当前的已知上限 |

## 结论

- 内核和数据库确定性保证的约定（事务、指纹、拒绝、完整目标、事件与消费者、0007 不变量），三个 agent 都没有做错。AGENTS.md 中写明的锁协议和数据库触发器扩展，三个 agent 也都遵守了，唯一的例外是 amend 漏掉了数据库层的金额上限。
- 失败集中在平台没有表达的地方：
  - 需求边界：上限多加或少加；
  - 跨层同步：界面、文档、smoke 脚本；
  - 行为层面的版本纪律。
  
  前两类大多能靠更明确的 AGENTS.md 加确定性脚本减少；行为层面的版本纪律需要新的机制，例如为每个已发布版本保留固定的行为测试。
- 所有提交都通过了 AGENTS.md 规定的检查，但都被独立 review 判定为 FAIL。只用"检查通过"作为完成标准是不够的。
